## ADR-006 (2026-11-08, 채택) 닫힌 원본 세그먼트 gzip 압축
- **맥락:** 1시간 실측(2026-11-08, aaba1ac)에서 원본 JSONL이 1.45GB였습니다.
  - 그중 Upbit 체결 7일 백필(일회성)이 1.1GB입니다.
  - 상시 유입 추정치(하루): bookTicker 약 650MB, Upbit 호가 약 400MB, metrics 약 690MB.
  - 실측 gzip-6 압축률: bookTicker 8.7배, Upbit 호가 19배, oi_hist 9배, trades 17배.
- **결정**
  - UTC 시간대가 끝나고 10분이 지난 세그먼트를 gzip-6으로 압축합니다(`capture/compress.py`, rest 프로세스에서 10분 주기, 스레드에서 실행).
  - 4MB 단위로 스트리밍하고, 원본 sha256과 압축 해제본 sha256이 일치할 때만 원본을 지웁니다.
  - Windows에서 다른 프로세스가 파일을 쓰고 있으면 지우지 않고 다음 실행 때 다시 시도합니다.
  - writer는 시간대가 끝나면 쓰기가 없어도 파일을 닫습니다.
- **근거:** 설계 v2.1 "T0 원본은 압축해 영구 보관"과 디스크 상한 200GB. 압축 후 추정량은 하루 약 200MB, 연 약 73GB입니다.
- **영향:** 원본을 읽는 쪽(작업 7 컴팩터)은 `.jsonl`과 `.jsonl.gz`를 모두 읽어야 합니다. 꼬리 격리는 열려 있던 `.jsonl`에만 해당합니다.

## ADR-011 (2026-11-09, 채택) T0 봉인 비율 사전 등록 (설계 v2.1 §9-2: "T0 비율은 수집 시작 시점에 확정")
- **기준 시각:** T0 첫 수집 `T0_START_NS = 1794133310767502700`(2026-11-08 10:05 UTC 무렵, 1시간 실측 시작)
- **epoch 1(모든 T0 데이터셋 공통)**

  - 봉인 holdout: `[시작+60일, 시작+90일)`
  - 비율 2:1
- **근거:** T0 데이터는 이력이 수집 시작부터만 존재합니다. 시작 직후부터 연구할 수 있게 하려면 앞 구간을 연구에 쓰고, 뒤 구간을 사전에 봉인하는 방식이 필요합니다. 비율과 길이는 검정력과 무관하게 정한 **사전값**입니다.
- **고정 방식:** `catalog.db`의 `seal_policy`에 기록했고, SQL 트리거로 수정·삭제를 막았습니다.
  - 다음 epoch는 경계가 뒤로 가지 않게 연속 번호로만 추가할 수 있습니다.
  - 벌크 데이터셋(작업 8)의 epoch 1은 등록할 때 같은 방식으로 사전 등록합니다(제안: 연구 ~2026-05-01, holdout 2026-05-01~2026-11-01).
- **lag 사전값(bootstrap)**
  - 이벤트형 실시간 데이터: 0(관측 `received_at` 사용)
  - 5분 지표(시각 의미 미확인): 구간 시작으로 간주 + 1구간(300초)

- **유니버스:** 시점별 상위 100(직전 월 거래대금 기준), 상장폐지 심볼 포함
  - 합집합: 632개 심볼(923개 USDT 무기한 중). REST가 모르는 5개 심볼은 벌크 1d로 복구했습니다.
  - 다운로드 범위: 편입 기간 + 준비 기간 3개월
  - 용량: 1분봉 zip 15.5GB, 4종 합계 약 40GB(추정. ETH 기준 mark 55%, index 57%, premium 44%)
- **품질 발견:** 2026-10 월간 파일이 불완전합니다(BTCUSDT 1분봉 1일, mark·index·premium 2일 누락). catalog gap(cause `unknown`)으로 등록했습니다. 원본이 재생성되면(LastModified 변경) 새 버전으로 받습니다. 일간 파일로 메우는 것은 이후 과제입니다.

## ADR-014 (2026-11-09, 채택) 벌크 다운로드 실행 방식과 자원 한도
- **실행 방식:** Claude 세션 밖의 작업 스케줄러 작업으로 실행합니다(사용자 결정 1번). 일반 사용자 권한, 우선순위 7, 30분마다 재시도, 7일 동안 반복합니다.
- **자원 한도(초기값, 로그의 실측으로 다시 조정)**

  - 프로세스 private 메모리 1GB 초과면 중지(실측 최대 254MB의 약 4배)
  - 디스크 여유 50GB 미만이면 중지

## ADR-015 (2026-11-09, 채택) Upbit 1분봉 백필 설계 (작업 9)
- **API 실측:** `to` 이전에 실제로 존재하는 봉을 최대 200개 반환합니다(시간 창 방식이 아님). 그래서 연속으로 받은 두 봉 사이의 빈 분은 확정적으로 체결이 없었던 분입니다. 이 구간은 gap(cause `no_trade`, detail=마켓)으로 병합해 기록합니다. 상장 이전 구간은 gap이 아닙니다.
- **저장**
  - 청크(기본 50페이지)마다 불변 Parquet 하나를 씁니다.
  - catalog `backfill_chunk`와 no_trade gap을 하나의 트랜잭션으로 기록합니다(마이그레이션 0004).
  - 재개는 마켓별로 가장 오래된 청크에서 이어 갑니다. 완료는 `backfill_done`에 기록합니다.
- **시각:** 봉에는 `received_ns`가 없고 `fetched_ns`만 있습니다. 과거 봉을 실시간으로 관측한 것이 아니므로, 사용 가능 시각은 모델로 계산합니다(시작 + 1분 + lag 60초).
- **실행 겹침:** 파일럿과 본 실행처럼 끝 시각이 다른 실행이 겹치면, 리더가 (market, event_ns) 단위로 중복을 제거합니다. 값이 바뀐 행은 버전으로 남깁니다.
- **봉인:** 벌크와 같은 경계를 씁니다(ADR-013).
- **유니버스:** 현재 KRW 24시간 거래대금 상위 20입니다. 상장폐지 마켓은 포함하지 않으므로 생존 편향이 있습니다. 상장폐지 마켓의 캔들을 조회할 수 있는지는 **미확인**입니다.
- **레이트:** 초당 6회 이하로 요청합니다(candle 그룹 한도 10/s, 600/min). Upbit 418이 오면 즉시 중지합니다(exit 5).
- **한계:** 2026-11-08 17:00~22:00Z처럼 거래소 전체가 멈춘 시간도 봉이 없으므로 `no_trade`로 기록됩니다. 거래소 장애와 체결 없음은 캔들만으로 구분할 수 없습니다.

## ADR-016 (2026-11-09, 채택) 수신 공백 감지(작업 10 일부)와 절전 정책
- **수신 공백 감지**
  - 1초 주기 소스(`binance.um.book_ticker_1s`, `upbit.orderbook_l1_1s`)에서 연속 수신 간격이 30초를 넘으면 gap으로 기록합니다(`unknown`/`receive_gap`).
  - 프로세스 재시작 gap과 함께, 절전, 네트워크·거래소 장애, 프로세스 정지를 모두 잡습니다.
  - 연구 단계에서는 같은 시간대의 다른 실시간 소스(강제청산 포함)도 이 gap을 기준으로 결측으로 취급합니다.
- **실행 위치:** 컴팩션과 같은 자식 프로세스 방식으로 실행합니다. 수집기 메모리 상한을 지키고, Polars를 쓰지 않습니다.
- **절전 정책:** OS 전원 설정은 사용자 지시("운영체제의 다른 설정은 변경하지 마라")에 따라 변경하지 않습니다.
  - 절전 중에는 실시간 데이터가 영구히 손실됩니다. 이 SSD는 절전 중 BSOD 이력이 있습니다(메모리 ssd-overheat-bsod).
  - 따라서 수집 중에는 전원을 연결하고 "절전 안 함"으로 두는 것을 권장합니다. 변경은 사용자가 직접 하거나 별도로 승인합니다.

## ADR-017 (2026-11-09, 채택) 모니터·incident·알림 (작업 10)
- **위치:** rest 작업 프로세스의 5분 주기 job입니다. 판정은 순수 함수가 하고, 결과는 카탈로그 `incident` 테이블에 기록합니다.
  - 키마다 열린 incident는 1개입니다. 계속 실패하면 갱신하고, 심각도가 오르면 다시 알리고, 해소되면 닫습니다.
- **알림:** 새로 열렸거나 심각도가 오른 incident만 `run/alerts.log`에 남기고, 로그온 세션에 Windows 토스트를 띄웁니다.
  - 숨긴 PowerShell을 ShellExecuteW로 실행합니다. 문구는 JSON 파일로 넘겨 명령줄 인용 문제를 피합니다.
- **임계값(초깃값, incident 기록을 보고 재조정):** 하트비트 120초, 디스크 50GB(경고)/20GB(심각), RAM 1GB, 시계 250ms·5분, SSD 상태 30분, 수신 공백 5분
- **한계:** rest 프로세스 자신이 멈춘 경우(hang)는 감지하지 못합니다. 죽은 프로세스는 supervisor가 재시작하고, ws와 rest가 서로를 확인하는 감시는 하지 않습니다.
- **basis -4104:** TradFi 계약에는 basis가 없습니다. 첫 응답에서 (소스, 심볼)을 지원하지 않는 것으로 등록하고, 해당 프로세스가 사는 동안 건너뜁니다.

## ADR-020 (2026-11-09, 채택) 백테스트 엔진: 얇은 자체 엔진 두 개와 회계 규약 (Phase 2)
- **선택:** 설계 §12대로 자체 엔진을 씁니다.
  - NautilusTrader는 펀딩·증거금을 지원하는 이벤트 엔진입니다. 하지만 PIT 봉인 API, 버전이 붙은 lag, 시도 회계와 결합하려면 같은 작업이 다시 필요합니다.
  - vectorbt는 행렬 계산이라 펀딩 정산과 시점 정합을 모델링하기 어렵습니다(2026-11-09 웹 조사, 일부 미확인).
- **두 엔진은 회계 방식이 다르게 독립 구현했습니다.** 그래야 교차 검증이 의미가 있습니다.
  - 이벤트 엔진(기준): 수량과 현금으로 회계합니다. 시간 손절, ATR 손절(ATR 14), 청산(구간 mark 고저, 격리 증거금 = 자산/n)을 처리합니다.
  - 벡터화 엔진(선별): 가중치로 회계합니다. 종목 축은 행렬 연산, 시간 축은 1차원 반복입니다. 상태 없는 규칙만 지원하고, 청산이 가능했던 구간은 `liquidation_unmodelled`로 표시해 거부합니다.
- **규약**
  - 결정 d_k = 봉 시작 + timeframe + 1분입니다. as-of 봉만 사용합니다.
  - L1 체결가는 d_k + 지연 시점의 1분 시가입니다.
  - 목표 가중치 → 수량 q = w·E/P이며, **매 결정 시점마다 목표 가중치로 재조정**합니다.
  - 결측 구간에서는 주문하지 않고 포지션을 유지합니다. 최악 가정 버전은 결측 구간 보유분에 구간 고저폭(데이터가 없으면 10%)만큼의 손실을 더해 따로 계산합니다.
  - 마지막 결정 시점에 전부 청산합니다.
- **fidelity**
  - L0: 봉 종가 체결, 비용 없음. 연구 상한이며 채택에 쓰지 않습니다.
  - L1: 위 규약과 비용, 펀딩, 청산
  - L2: aggTrades가 없어 거부합니다.
  - 사후 검사: 평균 보유가 1시간 미만이면 L2가 필요하므로 거부합니다(§9-5).
