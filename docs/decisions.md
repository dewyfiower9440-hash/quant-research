## ADR-003 (2026-11-08, 채택) 선물 bookTicker는 REST 1초 폴링으로 수집
- **맥락:** Phase 0 실측 결과는 다음과 같습니다(`docs/measurements/phase0.md` 1·2절).
  - WS 상위 20심볼: 초당 1,550 메시지, 원본 하루 27GB(추정), 코어 약 0.5개 상시 사용
  - REST 전 심볼(804개) 1회: 121KB, 30회 CPU 0.3초(코어 약 1%), weight 여유 큼, 응답에 이벤트 `time` 포함
- **선택지**
  - (a) WS 원본을 받아 초 경계로 샘플링
  - (b) REST로 1초마다 전 심볼을 받아 상위 K만 저장
- **결정:** (b)
- **근거:**
  - 노트북의 발열과 CPU 부담을 크게 줄입니다(SSD 과열 이력).
  - 전 심볼을 관측할 수 있습니다.
  - `time` 필드를 `event_time`으로 쓸 수 있습니다.
- **대가**
  - 샘플 시점에 네트워크 지터(RTT 약 40ms)가 섞입니다. `received_at`과 `time`을 함께 저장합니다.
  - 수신량이 하루 약 10GB입니다. 가정용 회선이라 문제없다고 판단하지만 **미확인**입니다.
  - 초 내부의 미시구조 정보는 잃습니다. 분~일 시간축에는 충분합니다.
- **재검토 조건:** 초 단위 미시구조 가설이 생기면 해당 심볼만 WS로 수집합니다.

## ADR-005 (2026-11-08, 채택) 시계 기준과 벌크 metrics의 시각 해석
- **시계 기준:** Binance `/api/v3/time`을 씁니다(실측 offset −16ms, RTT 42ms). Upbit은 `Date` 헤더 해상도가 1초라 기준으로 쓰지 않습니다.
- **metrics `create_time`:** 공식 정의가 없어 구간 시작인지 끝인지 미확인입니다. **구간 시작으로 보수적으로 가정**합니다(가용 시각 = `create_time` + 5분 + lag). 근거는 설계 v2.1 §5.4입니다.

## ADR-006 (2026-11-08, 채택) 닫힌 원본 세그먼트 gzip 압축
- **맥락:** 1시간 실측(2026-11-08, aaba1ac)에서 원본 JSONL이 1.45GB였습니다.
  - 그중 Upbit 체결 7일 백필(일회성)이 1.1GB입니다.
  - 상시 유입 추정치(하루): bookTicker 약 650MB, Upbit 호가 약 400MB, metrics 약 690MB.
  - 실측 gzip-6 압축률: bookTicker 8.7배, Upbit 호가 19배, oi_hist 9배, trades 17배.
- **결정**
  - UTC 시간대가 끝나고 10분이 지난 세그먼트를 gzip-6으로 압축합니다(`capture/compress.py`, rest 프로세스에서 10분 주기, 스레드에서 실행).
  - 4MB 단위로 스트리밍하고, 원본 sha256과 압축 해제본 sha256이 일치할 때만 원본을 지웁니다.
  - Windows에서 다른 프로세스가 파일을 쓰고 있으면 지우지 않고 다음 실행 때 다시 시도합니다.
  - writer는 시간대가 끝나면 쓰기가 없어도 파일을 닫습니다.
- **근거:** 설계 v2.1 "T0 원본은 압축해 영구 보관"과 디스크 상한 200GB. 압축 후 추정량은 하루 약 200MB, 연 약 73GB입니다.
- **영향:** 원본을 읽는 쪽(작업 7 컴팩터)은 `.jsonl`과 `.jsonl.gz`를 모두 읽어야 합니다. 꼬리 격리는 열려 있던 `.jsonl`에만 해당합니다.

## ADR-007 (2026-11-08, 채택) 30일 지표 재수집 주기
- **맥락:** 30일 전체 재수집 1회는 원본 약 270MB입니다(5개 엔드포인트 × 50심볼 × 18페이지, basis 포함 시 6개). 6시간마다 반복하면 하루 1GB를 넘습니다.
- **결정:**
  - **전체 30일 재수집은 하루 1회** 합니다(재수정 이력 확보).
  - **매시간에는 최근 1페이지(500행, 약 41.7시간)**만 받습니다(신선도와 가용 지연 관측).
- **근거:** 재수정은 주로 최근 구간에서 일어난다고 가정합니다(**미확인**). 하루 1회 전체 패스로 그보다 오래된 재수정도 잡습니다.
- **검증 방법:** 작업 7 정규화 단계에서 버전이 바뀐 행의 분포(언제 기록된 행이 재수정되는지)를 실측하고, 이 가정을 재평가합니다.

## ADR-008 (2026-11-08, 채택) 상시 실행과 임시 백업
- **상시 실행:** 사용자 승인(2026-11-08)에 따라 작업 10의 작업 스케줄러 등록을 작업 4 직후로 앞당겼습니다.
  - 작업 이름 `qr-collector-supervisor`, 일반 사용자, `LogonType Interactive`, `RunLevel Limited`, 저장된 비밀번호 없음
  - 실행 파일 `pythonw.exe`(콘솔 창 없음), 로그는 `C:\dev\qr-data\logs\<role>.log`
  - 트리거: 로그온 + 5분 반복(F-006)
  - **제약:** 사용자가 로그인해 있을 때만 실행합니다. 재부팅 뒤에는 로그인해야 재개됩니다. 로그인 없이 실행하려면 S4U나 비밀번호 저장, 또는 관리자 등록이 필요하고, 이는 승인 범위 밖입니다.
- **중복 방지:** 작업 설정 `IgnoreNew`와 프로세스별 잠금(`run/*.lock`)을 둡니다. 수동 실행은 exit 2로 거부됩니다.
- **정상 종료:** `C:\dev\qr-data\run\STOP` 파일을 만들면 됩니다. 작업 스케줄러는 5분 뒤 다시 시작하려 하지만, 시작과 동시에 STOP을 지우고 다시 돕니다. 따라서 **완전히 멈추려면 먼저 작업을 비활성화**(`Disable-ScheduledTask qr-collector-supervisor`)한 뒤 STOP 파일을 만들어야 합니다.
- **임시 백업:** `C:\dev\qr-backup`(같은 SSD)에 매시간 증분 백업합니다(sha256 manifest).
  - **SSD 고장은 막지 못합니다.** 외부 대상이 정해지면 `backup_root` 설정만 바꿉니다.
  - 외부 장치 현황(2026-11-08): 연결된 외장 디스크 없음. OneDrive 개인 계정은 로그인과 동기화 중(용량 한도 미확인)

## ADR-009 (2026-11-08, 채택) 관리자 권한 사용 범위: 읽기 전용 조회 1회만
- **실행:** `tools/admin_probe_readonly.ps1`을 UAC 승인을 받아 1회 실행했습니다(23:19 KST). **변경 없음.** 결과: `C:\dev\qr-data\measurements\admin-probe-20261108T141902Z.json`
- **SSD:** KLEVV C710 현재 63°C, 한계 100°C, Wear 0. PowerOnHours와 오류 카운터는 장치가 보고하지 않습니다.
- **시계(w32time)**
  - 상태: NTP 동기화됨(stratum 5, time.windows.com, 마지막 동기화 17:52, 위상 오프셋 −0.4ms)
  - 간격: SpecialPollInterval 32768초(약 9.1시간)
  - 특이 사항: 마지막 동기화 오류 기록("정확하지 않은 시간 데이터")이 있고, 루트 분산이 7.8초입니다.
  - 수집기가 1분마다 잰 Binance offset은 −3.5~−16ms입니다.
- **결정:** 시계 설정을 **바꾸지 않습니다**(필요가 확인되지 않음). offset이 250ms를 넘는 구간이 실제로 생기면 `w32tm /config` 변경을 다시 제안합니다.
- **보류(사용자 결정 필요):** SSD 온도를 주기적으로 감시하려면 관리자 권한이 필요하므로, 관리자가 만든 예약 작업이 있어야 합니다. 이 작업은 읽기 전용 조회를 10분마다 실행해 JSON으로 기록합니다. 벌크 다운로드(작업 8) 전에 필요한지 결정이 필요합니다.
